The harness is the tool for intention and focus. It gives the horse the two things it doesn't have on its own: reach, and restraint.
03 · What's a harness
A chat window is a harness with none of this

The harness adds two things

Reach.
Tools. A shell. The file system. The loop that lets the model do something, look at what happened, and do the next thing.

Let's be clear about this — a bare model can't open a file, run a build, or check its own work. It isn't wild. It's inert.
Restraint.
Permissions. Context limits. Hooks. Skills and agents that say how work gets done around here.

The harness and everything you put in it are yours. The model is rented. Remember that one; it comes back later.

04 · The model landscape
By kind, then by where it comes from

The categories outlive the model names

Tool-calling
Can drive a harness: read, write, run, check. The only kind that matters for an agent. Most frontier and open-weights models now qualify.
Coding
Tuned on code and repos. Claude, GPT and Gemini at the top; Qwen Coder, DeepSeek and North Mini Code as open weights.
Image and 3D
Flux, Imagen and GPT Image for 2D. Meshy, Tripo, Rodin and Hunyuan3D for meshes. A different pipeline, and a different conversation, later.
Frontier, US
Anthropic's Claude, OpenAI's GPT, Google's Gemini, Meta's Muse Spark. Closed weights, hosted, the strongest planners.
Open weights, China
Qwen 3.8, DeepSeek V4, Kimi K3, GLM-5.3. Run them anywhere, including your own box. Read the licence.
Canadian
Cohere's Command A+ and Command A, out of Toronto. North Mini Code: 30B, Apache-2.0, runs locally. It exists, and it's a lot closer to home.
Model names as of 2026-09-20. The six categories will still be here next year. Some of the model names won't.
04 · The model landscape
One endpoint, every model

OpenRouter, and the "auto" model

The on-ramp.
One API key instead of accounts at five labs. Every model on the last slide, behind one URL.

openrouter/auto picks the model for each prompt, "powered by the wisdom of the market" — which is to say, whatever the crowd is spending on this week, by task type.

It's the fastest way to experiment. Use it tonight.
The catch.
You no longer know which model touched your code.

That matters for cost (a hard problem routed to a frontier model bills like one), for consistency (your agents and skills are tuned to a model's habits), and for sovereignty (where did your repo just go?).

Experiment on auto. Build on a pinned model.

Agent. A persona with its own rules, tools and context that you hand a job to.
agents/art.md
---
name: art
description: Art, a senior art director.
  Takes a stated vision and constrains it
  into an enforceable art bible…
model: opus
color: green
---
You are **Art**, a senior Art Director…
**Process** intake → interrogation
  (five questions, max) → the reduction
  → systems → art bible → enforcement.
Both are Markdown with a frontmatter block. No code. That's the whole trick, and it has to be said: it's a good one.

Decisions worth flagging to you.

06 · Workflow, and choosing a harness
Why I keep ending up back in a terminal

Close to the input, close to the output

Terminals are fast.
They hold you right next to the prompt, the output, and the result of every tool call. Cut and paste between five sessions in herdr. SSH into another box. Git is right there.

Sure, the terminal costs you a day of discomfort. That day is the price of everything after it.
Desktops hide and simplify.
And somehow end up more complicated. In Claude Desktop I don't know where I'm supposed to do what, and when it works on a codebase I can't tell you where my changes actually landed. Same with Buzz.

A chat window with a repo attached is still a chat window.
My daily loop: plan in the vault, grill the plan, init the folder, implement in small commits, review, repeat.

08 · Good architecture
Architecture is for the two parties who still have to work in the code: the agent, and the team

When is a codebase ready for an agent?

  • When it's indexed. The codebase-memory skill builds a knowledge graph of the functions, classes and calls, so "who calls this?" is a query the agent runs, not a hundred files it reads.
  • When it builds from one command. The agent runs the build exactly the way you do. No clicking through an editor.
  • When it tests from one command. The tests sit beside the modules and map back to the scenarios in the plan.
  • When the plan is in the repo. AGENTS.md, the GDD, the art bible. The agent reads them at the start of every task.
  • When the agent can see what it did. A dev server, a screenshot tool, a render script, a log it can search.
One more thing. AI is not the best tool for walking a tree, parsing a file, or rote replacement such as linting and renaming. It can do those things. Should it? Use the linter, and save the model for the parts that need judgement.

The Back End
Strictly speaking, a game only needs a game

"I can't do server stuff" is over

  • A box that's always on, or a tunnel to one. A $2 VM, a Pi, a Halifax host.
  • An API the agent scaffolds: REST or WebSocket, same session as the client.
  • CI that builds every push. Snail's Pace publishes an Android build on every merge.
  • A kill switch. Because live ops.
  • A plan for success. Scale is a good problem to have.
Snail's Pace has no server of its own. The race syncs between two phones over Nostr relays, and the invite is a link the studio site serves. A protocol did the back end. That's not a trick — that's the point of a protocol.

Prompt and Context Tips
The slide you photograph

Seven things I actually do

  • Write the plan to a file and point the agent at it. Never re-explain it in chat.
  • Name the layer you mean. "The HUD," not "the score thing."
  • Grill before building. The agent asks, you answer, the plan closes.
  • Commit small. One issue per task, one branch per issue.
  • Keep AGENTS.md current. It's the only memory that survives the session.
  • Let the agent see its own output: tests, renders, screenshots, logs.
  • Pin a model. Experiment on auto, build on one you know.
12 · Prompt and context tips
And three more, about context itself

Knowledge that doesn't leak

  • More context is always better. More of the right context. Read the plan, the GDD, the art bible, the last commit.
  • Write skills that update themselves. When the agent works something out the hard way, the last step is: write it to a skill. That knowledge is yours now, not the session's.
  • Format agent-facing text as Simplified Technical English. ASD-STE100 is the standard aerospace uses so a maintenance instruction can't be misread. An agent reading another agent is in exactly the same position.

12 · Prompt and context tips
The counterweight to "more context is better"

Keep your eye on the context window

  • It fills up faster than you expect. Every file the agent reads, every tool result, every screenshot goes into the window and stays there.
  • Watch the status line. The harness shows you how much of the window is left. Most people don't look at it until it has run out.
  • Compaction loses things. When the harness summarizes the conversation to make room, the specific detail you cared about is usually what gets dropped.
  • Hand off instead of pushing on. Write the current state to a file, start a fresh session, and point the new session at that file.
  • Scrollback is not context. The plan in the repo is context. The argument you had with the agent an hour ago is not, and it will not survive.

Sovereignty, and Why
It's a Thing Now
Three risks and one hedge

Whose model is it, anyway?

  • Your IP crosses a border on every API call. In a trade war, a model can become an illegal export overnight. There is no local copy of Claude.
  • The provider can change the deal. Terms, pricing, what they train on. Meta's contributor tier trains on your sessions. Do you want to train their models with your ideas?
  • The model can be retired. The one your skills were tuned to. And DeepSeek's API sends your repo to a company that answers to Beijing. Are you fine with that?
  • The hedge: keep the plan, the skills and the context in your own repo, so any model can pick them up. Know how to run an open-weights model locally, even if you rarely do.
