03 · what's a harness
a chat window is a harness with none of this

the harness adds two things

reach.
tools. a shell. the file system. the loop that lets the model act, look at what happened, and act again.

a bare model cannot open a file, run a build, or check its own work. it is not wild. it is inert.
restraint.
permissions. context limits. hooks. skills and agents that say how work is done here.

the harness and what you put in it are yours. the model is rented.

one endpoint, every model

openrouter, and the "auto" model

the on-ramp.
one api key instead of accounts at five labs. every model on the taxonomy slide behind one url.

openrouter/auto picks the model for each prompt, "powered by the wisdom of the market": what the crowd is spending on this week, by task type.

the fastest way to experiment. use it tonight.

you no longer know which model touched your code.

that matters for cost (a hard problem routed to a frontier model bills like one), for consistency (agents and skills are tuned to a model's habits), and for sovereignty (where did your repo just go).

06 · workflow and choosing a harness
why i keep ending up back in a terminal

close to the input, close to the output

terminals are fast.
they hold you next to the prompt, the output, and the result of every tool call. cut and paste between five sessions in herdr. ssh into another box. git is right there.

the terminal costs a day of discomfort. that day is the price of everything after it.
desktops hide and simplify.
and end up more complicated. in claude desktop i do not know where i should do what, and when it works on a codebase i cannot tell where my changes actually land.

a chat window with a repo attached is still a chat window.
my daily loop: plan in the vault, grill the plan, init the folder, implement in small commits, review, repeat.

08 · good architecture
architecture is for the two parties who still work in the code: the agent and the team

is this codebase ready for an agent

  • find where a thing lives. one system per folder, named what it is.
  • build it itself. one command, no clicking, no "it works on my machine".
  • test it itself. tests beside the module, mapped to the gherkin in the plan.
  • read the plan. agents.md, the gdd, the art bible, all in the repo.
  • see the result. a dev server, a screenshot tool, a render script, a log it can grep.
a 4,000-line game.js fails every one of these.

the back end
strictly speaking, a game only needs a game

"i can't do server stuff" is over

  • a box that is always on, or a tunnel to one. a $2 vm, a pi, a halifax host.
  • an api the agent scaffolds: rest or websocket, same session as the client.
  • ci that builds every push. snail's pace publishes an android build on every merge.
  • a kill switch. because live ops.
  • a plan for success. scale is a good problem, and the agent can read the bill.
snail's pace has no server of its own. the race syncs between two phones over nostr relays, and the invite is a link the studio site serves. a protocol did the back end.

prompt and context tips
the slide you photograph

seven things i actually do

  • write the plan to a file and point the agent at it. never re-explain in chat.
  • name the layer you mean. "the hud", not "the score thing".
  • grill before building. the agent asks; you answer; the plan closes.
  • commit small. one issue per task, one branch per issue.
  • keep agents.md current. it is the only memory that survives the session.
  • let the agent see its own output: tests, renders, screenshots, logs.
  • pin a model. experiment on auto, build on one you know.
12 · prompt and context tips
and three more, about context itself

knowledge that does not leak

  • more context is always better. more of the right context. read the plan, the gdd, the art bible, the last commit.
  • write skills that update themselves. when the agent works something out the hard way, the last step is: write it to a skill. that knowledge is now yours, not the session's.
  • format agent-facing text as simplified technical english. asd-ste100 is the standard aerospace uses so a maintenance instruction cannot be misread. an agent reading another agent is in the same position.

12 · prompt and context tips
the counterweight to "more context"

keep one eye on the window

  • it fills faster than you think. every file read, every tool result, every screenshot is in there.
  • watch the status line. the harness tells you how much is left; nobody reads it until it is gone.
  • compaction is lossy. when the harness summarises to make room, the detail you cared about is what goes.
  • hand off instead of pushing on. write the state to a file, start a fresh session, point it at the file.
  • scrollback is not context. the plan in the repo is context. the argument you had an hour ago is not.

13
sovereignty, and why
it's a thing now
three risks and one hedge

whose model is it anyway

  • your ip crosses a border on every api call. in a trade war, a model can become an illegal export overnight. there is no local copy of claude.
  • the provider can change the deal. terms, pricing, what they train on. meta's contributor tier trains on your sessions. are you happy training their models with your ideas?
  • the model can be retired. the one your skills were tuned to. deepseek's api sends your repo to a company that answers to beijing. are you fine with that?
  • the hedge: keep the plan, the skills and the context in your own repo, so any model can pick them up. know how to run an open-weights model locally, even if you rarely do.
